# Changelog

Each release's notes. From 1.0.0 on, a major or minor release has hand-written notes under `docs/releases/`, and the release workflow uses them as the release body. Older releases list their commits on GitHub.

## Unreleased

- DeepVariant 1.10.0 can run without the Small Model using `--deepvariant_disable_small_model true` (default `false`), or `DEEPVARIANT_DISABLE_SMALL_MODEL=true` for the calling script and launcher. The effective setting is logged. No-data command/cache tests and a BAM-only recovery plan cover the opt-out; the reported postprocessing failure's root cause and full-WGS outcome remain unproven.

- The Rust `og` binary has a first part of the summary collector: `og summary collect --only a`. It reads seven sections of summary.json (coverage, callability, sex_check, sample_qc, mosaic_sex_loss, read_count and variants), the run status, the manifest and each section's state. Nothing calls it yet: the reports still read the summary that `bin/collect_summary.py` writes. The sections are the same as the Python's on 33 parity cases, compared as JSON with key order. It walks the sample folder once instead of running a `glob` for each candidate path, and it reads step 33's table once for its two sections. On a synthetic 1,000,000-record VCF the variant count takes 0.05 s and 7 MB, where the Python collector took 0.9 s and 38 MB. What differs from the Python:
  - A file named `.vcf.gz` that is plain text is read. The Python marked the variants section unreadable.
  - A sample name with `*`, `?` or `[` is matched as written. The Python read it as a file pattern.
  - A run status whose start time is not a date (`nan`, `inf`) counts as having no start time. The Python stopped with a traceback and wrote no summary.
  - `--out` is required while the command reads a part of the sections. The Python wrote `summary.json` in the sample folder by default, and a part of the sections there would replace the complete summary the reports read.
  - A `.vcf.gz` whose deflate data is corrupt is still marked unreadable, but the note names the fault in the Rust reader's words (`corrupt deflate stream`), not zlib's (`Error -3 while decompressing data: ...`).

- Step 37's own Y tools now run in the Rust `og` binary: `og y tree-positions` and `og y tree-place` (the placement on the current YFull YTree), `og y private-snps` (the private SNP list) and `og y yleaf-positions` (Yleaf's marker positions). They replace `bin/y_tree_place.py` and `bin/y_private_snps.py`, which are gone, and the `positions` command of `bin/yleaf_run.py`, which keeps only `predict`. og is static, so each part still runs in the Yleaf image. The three tables are the same, byte for byte, on the 43 parity cases, except where a line below says otherwise. On the pinned YTree 14.06.0 with a synthetic pileup of 362,055 positions, `og y tree-place` takes 0.8 s and 99 MB where the Python took 3.6 s and 389 MB; on a synthetic chrY VCF of 20,000 records, `og y private-snps` takes 0.3 s and 24 MB where the Python took 1.1 s and 330 MB. What changes on purpose:
  - `og y tree-place` reads the pileup by contig and position, and only its `chrY` (or `Y`) lines. The Python keyed it by position only, so a line on another contig could overwrite a chrY count. Lines on another contig are now counted at the end of the step line, and a pileup with both `chrY` and `Y` lines stops with exit 1. Step 37 makes a chrY-only pileup, so its results do not change.
  - `og y private-snps` refuses a callable mask with more than one FASTA record (exit 1). The Python joined the records into one sequence, which shifts every position after the first. The pinned mask has one record.
  - A tree branch whose `id`, `snps` or `children` has a type the Python could not use, or that repeats one of those keys, stops `og y tree-place` with the branch named. The Python crashed or kept the last copy.
  - Each output is written to a temporary file and renamed, so a step that stops leaves no half-written table.
  - A gzip mask or VCF is told by its first bytes, not by a `.gz` name.
  - `og y private-snps --max-depth-factor nan` stops with exit 1. The Python took it and turned the depth gate off; `0` is the way to do that.

- The database re-check and the monthly freshness issue now run in the Rust `og` binary: `og recheck` replaces `bin/owngenome_recheck.py` and `og dev freshness` replaces `scripts/ci/freshness.py`, which is gone. `bin/owngenome_recheck.py` stays until 1.1.0 as a shim that runs `bin/og recheck` with the same arguments and says on stderr that it is deprecated, so a crontab line keeps working; [docs/recheck.md](docs/recheck.md) has the new lines. Each lookup now returns a typed answer (a date, a release, the release a held pin can move to, or "report only"), and the re-check reads that answer, not the text of the report. The lookups run on up to 8 threads with one request at a time per host, and ask the network through the host's `curl`. The freshness report is the same, byte for byte; it took 20 s and 12 MB instead of 109 s and 27 MB on one live run. On a synthetic sample with 5,000 PGS scores the re-check takes 0.05 s and 16 MB instead of 0.56 s and 33 MB, with the same `state.json` by content. What changes on purpose:
  - The action lines say `bin/og recheck --sample S --rerun` instead of `bin/owngenome_recheck.py --sample S --rerun`.
  - `--rerun` prints its own lines before the replayed command's output. The Python held its lines in a buffer, so they could come after the child's.
  - `og dev freshness` finds `scripts/lib/common.sh` beside the `versions.env` it reads when it runs outside a checkout.
  - `state.json` is written one item at a time, so a sample with many PGS scores never holds the whole document in memory.
  - After `--rerun`, the exit code counts the failed lookups of the check written last. The Python counted the check before the replay, so a score the replayed run added, whose lookup failed, still gave exit 0.
  - Each answer is written to a new folder that only the user can read, under a name nobody can guess. The Python used Python's own HTTP client and wrote no file.
  - Each HTTP attempt ends after 300 s in all, so a host that sends a byte a second cannot hold the check for ever.
